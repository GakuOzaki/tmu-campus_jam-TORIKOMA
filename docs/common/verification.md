# 完成条件を証拠で確かめる

「AIが完成と言った」「画面が表示された」だけでは完成にしません。[product.md](../product.md)のDoDごとに、実際の操作と期待結果を照合し、[verification.md](../verification.md)へ結果を残します。

## 1. 自動確認を実行する

[development.md](../development.md)に記録した確認コマンドを使います。mainには初期状態でアプリ・テスト・CIがないため、最初のタスクで、選んだ構成に必要な起動・品質確認・機能テストとCIをCopilotに用意してもらいます。たとえばnpmを選んだチームなら`npm run check`などのスクリプトを用意できますが、コマンド名はチームの構成に合わせます。

同じ変更・同じ環境に対して直近に実行し、成功を記録済みの確認は、その結果を使えます。未実施の場合や、確認結果に影響する変更・実行環境の変更があった場合は再実行します。自動確認が成功していても、手順2の学生による実操作は必要です。

実行する場合は、選んだ実行場所の別Terminalで行います。Copilot appで編集してCodespacesで実行する場合は、[変更を渡す手順](../copilot-app.md#codespacesへ変更を渡して確認する)で取り込んでから確認し、その結果をAppへ返します。

AIには、実行コマンドと成功・失敗の結果を示してもらいます。テストが企画のDoDを確かめているかも読みます。テストやCIが未作成・未実行なら「未確認」です。ワークフローが存在するだけ、ジョブがSkippedだっただけでは成功になりません。

結果には実行場所と実行環境の版も添えます。たとえばPCのNode.js 22での成功と、CIのNode.js 24での成功は別の記録です。CIの成功だけでPCも同じ版で確認済みとはしません。再確認後は現在の結果を更新し、過去の結果は日時・対象の変更を付けた履歴として区別します。

**まだPRを作っていない場合は、CIを「未確認」と記録し、このページの実機確認を先に進めます。** 手順4まで終えたら各環境の手順7で変更を保存してPRを作り、生成したCIがその変更に対して実行されたことを確認します。その実行URL・対象コミット・結果を[検証記録](../verification.md)へ追記します。CIが失敗した場合は、ログを基に修正して再確認します。実行自体が始まらない場合は、[Fork側のActionsとPR宛先](../choose-start.md#enable-actions)を確認します。

公開する場合は、[公開手順](publish.md)に沿って本番コンテナをビルド・起動し、起動確認と主要なDoDの確認も通します。PCにDockerを入れることは必須ではなく、CodespacesやCIで実行できます。

初回生成のサンプルテストは企画のテストへ発展させます。起動や画面配信など、選んだ構成に必要な基盤の確認も残します。不具合を直すために期待結果を都合よく緩めたり、失敗するテストを消して合格扱いにしたりしません。仕様変更が必要ならチームで理由を確認して文書とテストを更新します。

### 自動テストが失敗したら

ログの失敗したテスト名・期待結果・実際の結果を読みます。ブラウザテストを用意する場合は、失敗時の画像・操作記録を残す設定と、CIから取得する手順も生成し、保存先をdevelopment.mdへ記録します。Playwrightならスクリーンショットやtraceを使えます。生成時点で設定も記録もなければ、証拠が自動保存されるとは考えません。

Copilotへは、**失敗したテスト名、再現する入力・操作、期待結果、実際の結果**と、必要な画像や操作記録の確認結果を渡します。原因を直した後は同じテストを再実行し、結果を [verification.md](../verification.md) へ残します。テストにはダミーデータを使い、個人情報や秘密情報を記録へ含めないでください。

## 2. 実装した人とは別の学生が操作する

[development.md](../development.md)に記録した開発コマンドで起動し、PCでは記録されたローカルURL、Codespacesでは対応するポートの転送先を開きます。同じ変更・環境のサーバーが起動済みなら、その画面を使い、重ねて起動しません。CodespacesはPrivateのまま、同じPCで操作する人を交代して確認できます。[開発環境の説明](local-development.md)も参照してください。

手書きとFigmaの画面・遷移を見ながら、**必須DoDに対応する主要な操作経路を手動で確認**します。利用者の最初から最後までの操作を通し、各画面のボタン・移動・戻る操作、その機能に関係する空の状態や入力ミス、スマートフォン幅も試します。確認表へ経路と結果を記録してください。

追加の確認は、合意した機能に関係するものだけ選びます。次の例をすべてのチームの必須機能にする必要はありません。

| 機能・場面 | 見落としやすい確認例 |
| --- | --- |
| 入力した内容を表示する | 長い日本語だけでなく、連続した英数字もスマートフォン幅ではみ出さないか |
| 入力・保存・削除後に画面が変わる | キーボードのフォーカスを見失わず、次の操作へ進めるか。同じ名前の項目も操作対象を区別できるか |
| 日付で表示が変わる | 開いたまま日付が変わったときや、別のタブから戻ったときも更新されるか。時計を制御する自動テストで確認してもよい |
| ブラウザにデータを保存する | 再読み込み後も残るか。複数タブでの編集を対応範囲に含めるなら、別タブや同時の保存でデータが消えたり復活したりしないか |

対応範囲が曖昧ならチームで決め、productへ残します。今回の対象外とした条件と、対応予定だが未確認の条件は分けて記録します。

AIがブラウザを操作できる環境では、その確認も追加できます。AIによるブラウザ操作は任意です。学生による実操作を完成確認に含めます。

## 3. DoDと照合する

例えば「3件登録すると期限順に並ぶ」なら、期限が異なる3件を順不同で入力し、表示順を確かめます。「提出済みにすると一覧から消える」なら、実際に操作して対象が消えたことを確認します。

結果は次のように分けます。

| 状態 | 意味 |
| --- | --- |
| 未確認 | 実行していない、または必要な証拠がない |
| 未達 | 確認したが、期待結果を満たさない |
| 達成 | 操作・テスト結果で条件を満たすことを確認した |

未達は、再現する入力・操作、期待結果、実際の結果をCopilotへ渡して修正します。未確認が残っている場合も、確認してから完成を判断します。

[verify-goal](../../.github/skills/verify-goal/SKILL.md)で、条件の照合と修正を依頼できます。

```text
目的：
verify-goal スキルを使ってDoDと現在のアプリを照合し、未達なら原因を直して再確認してください。

文脈：
docs/product.md、docs/tasks.md、docs/development.md、docs/verification.md と現在のコード・テスト・操作結果を読んでください。

制約：
合意した範囲と期待結果を守り、選んだ実行場所で確認してください。
Appで編集しCodespacesで実行する場合は、確認方法を案内し、学生から結果が返るまで待ってください。
実行していない確認を成功扱いにしないでください。

完成条件：
DoDごとの達成・未達・未確認と、確認したコマンド・操作・結果・証拠が docs/verification.md に残っていること。
残る作業は docs/tasks.md に記録し、人の判断や環境の準備が必要なら次の操作を知らせてください。
```

## 4. チームで完成を判断する

必須DoDが達成され、主要な操作経路の手動確認を終えたら、確認した学生と結果を記録します。表示名に個人名を使う必要はありません。

Azure Container Appsへ公開した場合は、[公開手順](publish.md)に沿って公開URLでも操作します。開発中の確認、コンテナでの確認、Azure上の認証や外部サービス接続は、それぞれ実施した範囲を記録します。

最後に、想定した学生が困りごとを解決できそうかを振り返ります。アプリの動作確認と、解決策の仮説検証は別です。実際の利用者に確かめていなければ、仮説は未検証として発表します。

未達や未確認の操作が残ったら、[実装ループの手順3](build-loop.md#3-実装検証修正を続ける)へ結果を渡し、修正・確認を続けます。必須DoDと学生による操作確認を終えたら、[Codespacesの手順7](../codespaces.md#7-保存して共有し発表する)または[Copilot appの手順7](../copilot-app.md#7-変更を保存しprから発表へ進む)へ戻り、保存・PR・CI結果の記録を済ませます。その後は[発表と終了](presentation.md)へ進みます。すでに同じ変更のPRとCIを確認済みなら、その記録を使えます。
