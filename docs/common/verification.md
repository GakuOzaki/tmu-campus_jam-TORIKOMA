# 完成条件を証拠で確かめる

「AIが完成と言った」「画面が表示された」だけでは完成にしません。[product.md](../product.md)のDoDごとに、実際の操作と期待結果を照合し、[verification.md](../verification.md)へ結果を残します。

## 1. 自動確認を実行する

同じ変更・同じ環境に対して直近に実行し、成功を記録済みの `npm run check` と `npm run test:e2e` は、その結果を使えます。未実施の場合や、確認結果に影響する変更・実行環境の変更があった場合は再実行します。自動確認が成功していても、手順2の学生による実操作は必要です。

実行する場合は、選んだ実行場所の別Terminalで行います。Copilot appで編集してCodespacesで実行する場合は、[変更を渡す手順](../copilot-app.md#codespacesへ変更を渡して確認する)でCodespacesへ取り込んでから確認し、その結果をAppへ返します。

```bash
npm run check
npm run test:e2e
```

AIには、実行コマンドと成功・失敗の結果を示してもらいます。実行していない確認は「未確認」です。テストが企画のDoDを確かめているかも読んでください。

結果には実行場所と実行環境の版も添えます。たとえばPCのNode.js 22での成功と、CIのNode.js 24での成功は別の記録です。CIの成功だけでPCも同じ版で確認済みとはしません。再確認後は現在の結果を更新し、過去の結果は日時・対象の変更を付けた履歴として区別します。

`test:e2e` は本番用のNode.jsサーバーで画面とAPIを確認します。PRのGitHub Actionsでは、本番用コンテナをビルド・起動して同じブラウザテストを実行します。公開する場合は、このコンテナの確認も成功していることを確かめます。PCにDockerを入れることは必須ではありません。

最初の画面用の `tests/starter.spec.ts` は企画の機能テストへ更新し、API・画面配信の基盤テスト `tests/runtime.spec.ts` は残します。不具合を直すために期待結果を都合よく緩めたり、失敗するテストを消して合格扱いにしたりしません。仕様の変更が必要なら、チームで理由を確認してから文書とテストを更新します。

### 自動テストが失敗したら

まずログの失敗したテスト名・期待結果・実際の結果を読みます。画面の失敗時には、選んだ実行場所の `test-results/` にスクリーンショットと操作記録（`trace.zip`）が残ります。GitHub Actionsの場合は、失敗した **Check** 実行の **Summary → Artifacts → playwright-failure-evidence** から取得できます（保存期間は3日）。テスト開始前などの失敗では、これらのファイルが生成されない場合もあります。

Copilotへは、**失敗したテスト名、再現する入力・操作、期待結果、実際の結果**と、必要なスクリーンショットや操作記録の確認結果を渡します。原因を直した後は同じテストを再実行し、結果を [verification.md](../verification.md) へ残します。テストにはダミーデータを使い、個人情報や秘密情報を記録へ含めないでください。

## 2. 実装した人とは別の学生が操作する

`npm run dev`を起動し、PCでは `http://127.0.0.1:4280`、Codespacesでは4280番の転送先を開きます。CodespacesはPrivateのまま、同じPCで操作する人を交代して確認できます。[開発環境の説明](local-development.md)も参照してください。

手書きとFigmaの画面・遷移を見ながら、**必須DoDに対応する主要な操作経路を手動で確認**します。利用者の最初から最後までの操作を通し、各画面のボタン・移動・戻る操作、その機能に関係する空の状態や入力ミス、スマートフォン幅も試します。確認表へ経路と結果を記録してください。

追加の確認は、合意した機能に関係するものだけ選びます。次の例をすべてのチームの必須機能にする必要はありません。

| 機能・場面 | 見落としやすい確認例 |
| --- | --- |
| 入力した内容を表示する | 長い日本語だけでなく、連続した英数字もスマートフォン幅ではみ出さないか |
| 入力・保存・削除後に画面が変わる | キーボードのフォーカスを見失わず、次の操作へ進めるか。同じ名前の項目も操作対象を区別できるか |
| 日付で表示が変わる | 開いたまま日付が変わったときや、別のタブから戻ったときも更新されるか。時計を制御する自動テストで確認してもよい |
| ブラウザにデータを保存する | 再読み込み後も残るか。複数タブでの編集を対応範囲に含めるなら、別タブや同時の保存でデータが消えたり復活したりしないか |

対応範囲が曖昧ならチームで決め、productへ残します。今回の対象外とした条件と、対応予定だが未確認の条件は分けて記録します。

AIがブラウザを操作できる環境では、その確認も追加できます。AIによるブラウザ操作は任意です。学生による実操作を完成確認に含めます。

## 3. DoDと照合する

例えば「3件登録すると期限順に並ぶ」なら、期限が異なる3件を順不同で入力し、表示順を確かめます。「提出済みにすると一覧から消える」なら、実際に操作して対象が消えたことを確認します。

結果は次のように分けます。

| 状態 | 意味 |
| --- | --- |
| 未確認 | 実行していない、または必要な証拠がない |
| 未達 | 確認したが、期待結果を満たさない |
| 達成 | 操作・テスト結果で条件を満たすことを確認した |

未達は、再現する入力・操作、期待結果、実際の結果をCopilotへ渡して修正します。未確認が残っている場合も、確認してから完成を判断します。

[verify-goal](../../.github/skills/verify-goal/SKILL.md)で、条件の照合と修正を依頼できます。

```text
目的：
verify-goal スキルを使ってDoDと現在のアプリを照合し、未達なら原因を直して再確認してください。

文脈：
docs/product.md、docs/tasks.md、docs/verification.md と現在のコード・テスト・操作結果を読んでください。

制約：
合意した範囲と期待結果を守り、選んだ実行場所で確認してください。
Appで編集しCodespacesで実行する場合は、確認方法を案内し、学生から結果が返るまで待ってください。
実行していない確認を成功扱いにしないでください。

完成条件：
DoDごとの達成・未達・未確認と、確認したコマンド・操作・結果・証拠が docs/verification.md に残っていること。
残る作業は docs/tasks.md に記録し、人の判断や環境の準備が必要なら次の操作を知らせてください。
```

## 4. チームで完成を判断する

必須DoDが達成され、主要な操作経路の手動確認を終えたら、確認した学生と結果を記録します。表示名に個人名を使う必要はありません。

Azure Container Appsへ公開した場合は、[公開手順](publish.md)に沿って公開URLでも操作します。開発中の確認、コンテナでの確認、Azure上の認証や外部サービス接続は、それぞれ実施した範囲を記録します。

最後に、想定した学生が困りごとを解決できそうかを振り返ります。アプリの動作確認と、解決策の仮説検証は別です。実際の利用者に確かめていなければ、仮説は未検証として発表します。

未達があれば、選んだ環境の実装（[Codespacesの手順5](../codespaces.md#implementation)・[Copilot appの手順5](../copilot-app.md#implementation)）へ戻ります。確認を終えたら、[Codespacesの手順7](../codespaces.md#save-and-share)・[Copilot appの手順7](../copilot-app.md#save-and-share)で検証記録も保存・pushし、PRとCIを確認します。その後に[発表・振り返り・終了](presentation.md)へ進みます。
