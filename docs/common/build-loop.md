# 実装して、確かめながら完成へ進める

`main`コースは、企画に合う構成をCopilotと決めて作る教材です。最初からアプリは入っていません。[product.md](../product.md)で目的と完成条件をそろえ、選んだ技術と確認方法を[development.md](../development.md)に残します。

このページは[Codespaces](../codespaces.md)と[Copilot app](../copilot-app.md)に共通する進め方です。各ガイドで終えた計画や準備をやり直す必要はありません。依頼・情報・実行と検証の仕組みを整える理由は、[Copilotと開発する3つの工夫](ai-development-tips.md)で確認できます。

**現在の状態から始めます。** 構成や計画が未決定なら[手順1](#1-planで最小構成と確かめ方を決める)、計画済みで最小アプリをまだ作っていなければ[手順2](#2-最初の実装で動かして確かめる仕組みを作る)、初回の起動・確認を終えていれば[手順3](#3-実装検証修正を続ける)へ進みます。

## 1. Planで最小構成と確かめ方を決める

必要な企画・画面案と、既にある場合は関係するコードを渡します。最初は技術の候補を短く比べ、開発時間内に最初の操作が通る構成をチームで選びます。React + Viteに決め打ちする必要はありません。既に選んだ構成がある場合は、理由なく選び直しません。

```text
目的：
必須機能を完成させる最小構成と、作業・検証の計画を提案してください。

文脈：
docs/product.md、画面設計、docs/development.mdを読み、必要なら関係する既存コードも確認してください。

制約：
仕様や実行場所が未決定なら確認してください。
短い開発時間で確かめられる範囲に絞り、不要な機能や基盤を追加しないでください。
このPlanではファイルを編集せず、実装を始めないでください。

完成条件：
採用する構成と理由、作業ごとのDoD・依存する作業・確認方法を草案にしてください。
初回は最小アプリ、起動手順、必要なテストとPR用CIの作成を最初の実装タスクに含めてください。
未決定の点を示し、チームが確認できる計画になっていること。
```

チームは必須機能の漏れ、余分な仕組み、実行する場所を確認します。合意したら、編集できるモードへ切り替えて `docs/tasks.md` と `docs/development.md` へ保存します。作成前のコマンドは予定と明示し、実行可能な手順と区別します。小さな文言修正まで毎回計画を作り直す必要はありません。

## 2. 最初の実装で、動かして確かめる仕組みを作る

選んだ技術で最小アプリを作り、必要な依存関係、起動・終了、最初の完成条件を確かめるテストを用意します。同じ確認をPRで実行できるよう、GitHub ActionsのCIも作ります。型チェックやビルドが不要な構成にまで、それらを追加する必要はありません。

作成したコマンド、実行するディレクトリ、ポート、テストの準備、環境変数、CIの対象を `docs/development.md` に記録します。言語・実行環境を変える場合は `.devcontainer/` も合わせます。起動できたことと最初の操作の結果を確かめてから、次の機能へ進みます。[起動と確認の共通ガイド](local-development.md)

PCで実行するAppのSetup／Runは、この段階で実際のコマンドが決まってから必要に応じて作成します。Codespacesでのみ実行するなら、PC用のRunを準備する必要はありません。

## 3. 実装・検証・修正を続ける

各環境の手順5で実装依頼を送信済みなら、同じ依頼を重ねず、その作業と結果を引き継ぎます。次の依頼例は、まだ依頼していないときや、残る作業を改めて依頼するときに使います。

編集と実行が同じ場所なら、次を送ります。**Appで編集しCodespacesで実行する場合は、[App手順5](../copilot-app.md#5-interactiveで実装と確認を繰り返す)の依頼文を使います。** その経路では、学生のGUIでのcommit・push、Codespacesでの確認、結果の返却を待ってから修正を続けます。

```text
目的：
合意した計画の未完了タスクから実装し、完成条件まで検証・修正を進めてください。

文脈：
docs/product.md、docs/tasks.md、docs/development.mdと、作業に必要なコードを読んでください。

制約：
合意した範囲・採用構成・実行場所に従ってください。
追加支出、有料契約、秘密情報が必要になる作業は、実行前に対象と理由を説明してください。
権限不足、同じ不具合で進展がない場合、チームが決めた上限に達した場合は、試したことと再開に必要な情報を報告してください。

完成条件：
初回は最小アプリと必要な起動・テスト・CIを作り、実際の手順をdocs/development.mdに記録してください。
対応するDoDを確かめるテストを用意し、記録したコマンドと必要な操作で実際の結果を確かめてください。
失敗や未達は原因を直して再確認し、実行していない確認は未確認にしてください。
変更内容、実行した確認と結果、未達・未確認をdocs/verification.mdに残してください。
```

並び替えや入力チェックなど期待結果が明確な機能では、先にテストを作り、未実装時に期待どおり失敗することも確かめます。見た目や使いやすさは人の確認も使います。採用していないテストツールを一式追加することが目的ではありません。

CIがない、未実行、skipされた状態は成功ではありません。実際に必要な確認が動いた証拠と、確認できなかった理由を残します。見た目を整えただけで、保存や画面遷移まで完成したとは扱いません。

## 4. 完成条件に戻り、別の学生にも使ってもらう

AIの完了報告を[検証の進め方](verification.md)で確かめます。別の学生が必須DoDの主要な操作経路を実際に試し、未達なら修正へ戻します。必須機能に関係する空の状態・入力ミス・スマートフォン幅も確認します。

同じ変更・同じ環境で直前に成功し、記録済みの自動確認は繰り返す必要はありません。コード・仕様・実行環境を変えた場合や、未確認の条件が残る場合に必要な確認を行います。

仕様を変えたら、まず `product.md` の機能・DoD・対象外と画面設計を更新し、`tasks.md` とテストもそろえます。起動・確認方法を変えたら `development.md` も更新します。会話だけで仕様や実行方法を変えないでください。

同じ失敗を繰り返したら、[改善する場所の選び方](ai-development-tips.md#同じ失敗を繰り返したら何を直すか)を使い、依頼・資料・テスト・環境のどこを直すか考えます。原因に合う小さな改善をし、再確認した結果を残します。

## 5. 保存し、次の作業へ引き継ぐ

セッションや環境を切り替える前に、実装済み・未完了、確認結果、次の作業を文書に残してGitで保存します。次のAIは文書と現在の変更を読み、記録した実行場所で起動・基本動作を確認してから続けます。AppとCodespacesを分ける場合は、学生が返す実行結果を待ちます。

必須条件を確認できたら、選んだ環境の保存・PRの手順（[Codespacesの手順7](../codespaces.md#7-保存して共有し発表する)・[Copilot appの手順7](../copilot-app.md#7-変更を保存しprから発表へ進む)）へ戻ります。変更と確認結果を保存し、PRのCI結果も記録してから[発表と終了](presentation.md)へ進みます。Azureへの公開は、継続して共有するURLが必要なチームだけが選ぶ任意の分岐です。
