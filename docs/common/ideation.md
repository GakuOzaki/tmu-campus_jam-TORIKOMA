# 企画を決めて、開発へ渡す

テーマは「大学生のお困りごとを解消するプロダクト」です。まずチームで課題と解決策を決め、そのあとにAIへ開発を依頼します。事前講義では記入済みの[締切管理の例](../examples/deadline.md)を使い、本番では自分たちの企画に差し替えます。

## 1. 課題を広げて、絞る

授業、サークル、バイト、就活、友人関係、一人暮らしなどで面倒だった場面を各自で書き出します。付箋1枚に困りごと1つ。発散中は否定せず、他の人の案に乗っかって構いません。

似た困りごとをまとめ、投票の前に「起こる頻度」「解決しないと困ること」「今の対処とその不満」を確かめます。自分ごと度、他の学生の共感度、2日間で最低限作れそうかを基準に、取り組む課題を1つ選びます。選ばなかった案も残します。

## 2. 深掘りして、問いにする

できればチーム外の学生に、実際に困った場面と今の対処を聞きます。聞いて分かった事実と、チームが考えた仮説を分けて記録します。まだ聞いていないことは「未確認」と残し、AIに調査結果を作らせません。

「なぜ？」で原因を探しますが、回数だけで正解が出るわけではありません。原因も仮説として、聞けた事実と照らします。最後に次の問いへ変換します。

> どうすれば【誰】が【原因となっている状況】を解決して、【なりたい状態】になれるか？

## 3. 解決策を広げて、選ぶ

クレイジー8は、8分で8案をラフな絵や一言にする方法です。自動化、通知、共有、見える化など、違う切り口を試します。共有して案を組み合わせてから、「困りごとを解決する度」「2日で作れる度」「ワクワク度」で比べ、1案を選びます。必要な技術・データが使えるかも確かめます。

## 4. 企画と開発要件をそろえる

企画を次の1文にします。

> 【A：誰】が、【B：いつ・どんな場面】に【C：具体的な課題】で困っている。そこで【D：解決策】によって、その困りごとを解決する。

課題の重要性、既存の方法よりこの案を選ぶ理由、課題と解決策のつながりをチームで確認します。そのあとで、コンセプト、最大3つのコア機能、利用フロー、完成条件（DoD）、今回は作らないもの、AIの使い方を決めます。

DoDは「使いやすい」のような感想で終えず、「何を操作すると、どうなるか」まで書きます。実装できたことと、困りごとが解決するという仮説が確かめられたことは分けます。

データの保存・ほかの人との共有、ログイン、外部APIが必要かも、この時点で決めます。例えば「再読み込みしても残る」と「別の学生の端末にも同じ内容が見える」は別の条件です。必要な機能は最初からDoDと実装計画へ含め、使うサービスの権利や準備も確認します。

## 5. 手書きからFigmaへ進む

コア機能と利用フローに必要な画面を選びます。画面数は必要最小限にし、各画面の「表示するもの」「押すもの」「押した先」を紙に描きます。

手書きを見ながらFigmaに画面を作り、Prototypeでつなぎ、チームでクリックして一連の流れを確認します。見た目に加え、戻る操作や必要な画面・機能の抜けを確認してください。要件を合意してから、手書き → Figma → 実装の順で進みます。

## 6. 開発用の文書に整理する

ここまでの成果物は、**企画メモ、手書き・Figmaの画面案、操作と遷移の説明**です。決定したこと・仮説・未確認を分け、共有してよい内容を揃えます。個人名や私的な連絡を含む原本はコミットしません。

このあと各環境ガイドで、[元資料の置き方](../source/README.md)に沿って `docs/source/` に保存し、Planで[prepare-project](../../.github/skills/prepare-project/SKILL.md)を使って文書と実装計画の草案に整理します。企画・DoD・対象外は[product.md](../product.md)、作業順と確認方法は[tasks.md](../tasks.md)へ、チームの合意後に編集できるモードで保存します。
