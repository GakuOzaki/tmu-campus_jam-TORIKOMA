# Copilotと開発する3つの工夫

この教材では、**依頼の伝え方、判断に使う情報、実行して確かめる仕組み**を一緒に整えます。プロンプト → コンテキスト → ハーネスという言葉は、ここでは設計する範囲が広がる関係として扱います。3つは重なり合い、開発中はどれも使います。

| 観点 | 整えるもの | このリポジトリに入っている工夫 |
| --- | --- | --- |
| プロンプトエンジニアリング | 今回、何をどこまで頼み、どうなればよいか | 目的・範囲・完成条件・確認方法を含む依頼例、Planから実装への切り替え |
| コンテキストエンジニアリング | 判断に必要な情報を、必要なときに読める状態にする | 企画・開発方法・作業・検証の文書、画面PNGと遷移、必要な資料だけ読む指示、セッション間の引き継ぎ |
| ハーネスエンジニアリング | AIが実行・観察・検証・修正を進められる環境と流れ | Dev Container、アプリ生成後にそろえる実行・テスト・CI、失敗の記録、人による確認 |

これは各社共通の厳密な分類ではなく、教材を理解するための整理です。例えばSkillは必要な情報を渡す仕組みであり、繰り返す作業の手順でもあります。Copilot本体が持つ対話・ツール実行の仕組みに、リポジトリ側で資料・実行環境・検証方法を組み合わせています。

## 1. 依頼は「目的・文脈・制約・完成条件」を具体的にする

[![プロンプトエンジニアリングの図解：目的・文脈・制約・完成条件の4項目で依頼を具体化する。締切管理の依頼例と、この教材の対応ファイルを示す。](../images/prompt-engineering.png)](../images/prompt-engineering.png)

図はクリックすると拡大できます。図中の **Plan / Interactive** はCopilot appの呼び方です。CodespacesのCopilot Chatでは **Plan / Agent** を使います。

自分たちの目的・読む資料・対象外・完成条件を図に当てはめたら、選んだ環境のPlan（[Codespacesの手順4](../codespaces.md#planning)・[Copilot appの手順4](../copilot-app.md#planning)）へ戻り、依頼例を送ります。以下の説明と公式資料は、詳しく知りたいときに読めます。 **発表中の振り返りで開いた場合は、[発表ガイドの振り返り](presentation.md#3-copilotとの開発を振り返る)へ戻ります。**

[OpenAIの開発向けbest practices](https://learn.chatgpt.com/guides/best-practices#strong-first-use-context-and-prompts)は、依頼の基本として **Goal・Context・Constraints・Done when** の4項目を挙げています。この教材では、Copilotへの依頼を考える手がかりとして使います。

| 項目 | 学生が考えること | この教材で使う情報 |
| --- | --- | --- |
| 目的（Goal） | 誰が、何をできるようにしたいか | 利用者の困りごとと、今回変える動作 |
| 文脈（Context） | 何を読めば判断できるか | 合意した企画の該当箇所、関係する画面・コード・エラー |
| 制約（Constraints） | 今回の範囲と、守る条件は何か | 対象外の機能、維持する仕様、選んだ実行場所 |
| 完成条件（Done when） | 何を確かめれば、できたと判断できるか | DoDに対応する入力・操作・期待結果 |

必要なら、これに**報告形式**（変更内容・確認結果・未確認事項など）を添えます。これは[OpenAIの一般向けPromptingガイド](https://learn.chatgpt.com/docs/prompting#prompting-overview)のOutputも参考にした教材上の補足です。「OpenAIが定めた必須の5要素」という位置づけではありません。

[各環境のガイド](../../README.md)と共通手順の企画・計画・実装・検証の依頼例は、この4見出しでそろえています。**Planの完成条件は「チームが確認できる草案ができること」、実装の完成条件は「対応するDoDを実際に確かめること」**です。作業段階に合わせて、今回何ができればよいかを示します。

4項目は抜けを見つけるための手がかりです。小さな修正や再開では今回変わることを短く伝え、すでに共有した条件は参照で済ませます。毎回すべての見出しを埋めたり、長い指示文を貼り直したりする必要はありません。

例えば「締切アプリをいい感じにして」だけでは、何を変えるかと完成の判断が曖昧です。[締切管理の参考例](../examples/deadline.md)なら、次のように具体化できます。これは説明用の例なので、自分たちの企画に合わせて変えてください。

```text
目的：
締切の近い順に、次に取り組む課題を判断できるようにしてください。

文脈：
合意した docs/product.md の「期限順に一覧で見る」に対応する作業が対象です。
関係するコードとテストを読んで実装してください。

制約：
通知やログインは今回追加しません。確認はチームが選んだ実行場所で行ってください。

完成条件：
期限を10月22日、20日、21日の順に登録したら、20日、21日、22日の順に表示されることを確認してください。

報告形式：
変更内容、実行した確認、未確認のことを報告してください。
```

チームが決めた**利用者の結果**を伝え、必要な制約を添えます。実装する関数名や細かな編集順まで、毎回先回りして指定する必要はありません。曖昧さや複数ファイルへの影響が大きければPlanで相談し、小さな修正はその範囲で進めます。[共通の実装ループ](build-loop.md)を使ってください。

Appで編集しCodespacesで実行する場合は、この例でも[GUIで変更を渡す手順](../copilot-app.md#codespacesへ変更を渡して確認する)に従います。AIは確認コマンドを案内し、学生が返す結果を待ちます。

根拠：上記のOpenAIの4項目と、[GitHubのプロンプト設計](https://docs.github.com/en/copilot/concepts/prompting/prompt-engineering)が勧める目的・具体的な要件・入力と出力の例を、DoDと依頼例に反映しています。OpenAIの一般向けガイドも、必要な項目だけ使い、固定形式を必須にしないと説明しています。実装と確認結果を見て依頼を調整します。

### Anthropicの指針との対応

Anthropicの[Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)は、明確な指示、背景・理由、具体例、出力形式や制約を扱っています。[Prompt engineering overview](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/overview)では、改善の前に成功条件と検証方法を用意します。以下は、その考え方を教材の4項目へ対応づけたものです。Anthropicが同名の4項目テンプレートを定めているという意味ではありません。

| 教材の項目 | Anthropicの指針を生かす書き方 |
| --- | --- |
| 目的 | 依頼する作業と、欲しい結果を明確にする |
| 文脈 | 必要な資料に加え、なぜその動作が必要かを伝える |
| 制約 | 守る範囲と出力形式を具体的にし、順序が重要な作業だけ順番を示す |
| 完成条件 | 成功条件を先に決め、入力・操作・期待結果の例と検証方法を添える |

[Claude Codeのbest practices](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work)も、テスト・ビルド・画面比較など、結果を確かめる手段を渡すことを勧めています。この教材では、DoDの具体例、必要なテスト、画面と操作の確認に反映しています。例えば期限順の正常な入力に加えて、空の一覧や不正な入力も、その機能に必要なら確認します。Copilotではこれらの共通する考え方を使い、モデル固有の設定やXMLタグによる記法は必須にしていません。

## 2. 情報は正本を決め、必要な部分を渡す

[![コンテキストエンジニアリングの図解：企画・開発方法・作業・検証結果の正本を分け、必要な情報を参照し、決定と結果を次のセッションへ引き継ぐ。](../images/context-engineering.png)](../images/context-engineering.png)

会話が長くなっても、次のセッションが現在の決定を読めるようにします。

図で元資料と決定の保存先を確認したら、資料を渡す作業（[Codespacesの手順3](../codespaces.md#prepare-materials)・[Copilot appの手順4](../copilot-app.md#prepare-materials)）へ戻ります。作業の再開時に読んでいる場合は、[引き継ぎの確認](build-loop.md#5-保存し次の作業へ引き継ぐ)へ進みます。 **発表中の振り返りで開いた場合は、[発表ガイドの振り返り](presentation.md#3-copilotとの開発を振り返る)へ戻ります。**

| 場所 | 役割と使い方 |
| --- | --- |
| [product.md](../product.md) | 合意した企画・DoD・対象外。仕様を変えたらここを更新する |
| [development.md](../development.md) | 選んだ構成の実行環境・起動・確認コマンド・ポート・環境変数・公開方法。生成して確かめた内容を記録する |
| [tasks.md](../tasks.md) | 今回の作業、依存、残りの作業。再開時に今どこまで進んだかを読む |
| [verification.md](../verification.md) | 実際の結果と証拠。達成・未達・未確認を分ける |
| [source/](../source/README.md) | 関係する企画メモ、画面PNG、操作・遷移。AIが開けないURLだけで済ませない |
| [copilot-instructions.md](../../.github/copilot-instructions.md) | 共通ルール、資料の場所、起動・確認方法への案内。企画全文や会話全文を詰め込まない |
| [prepare-project](../../.github/skills/prepare-project/SKILL.md)・[verify-goal](../../.github/skills/verify-goal/SKILL.md) | 企画整理や完成確認が必要なときに参照する手順 |

初回には企画と構成の全体像を把握し、その後は今回の作業に必要な情報から読みます。依頼の「文脈」には、参照するファイルや対象のDoD・タスクを示します。必要な情報が足りなければ、関連する資料やコードを追加で調べます。

| 場面 | 主に読む・渡す情報 |
| --- | --- |
| 企画を整理する | 企画メモ、画面案、決定事項と未決定事項 |
| 機能を実装する | 対象タスク、対応するDoD、関連する画面・コード・テスト |
| 不具合を直す | 再現する入力・操作、期待結果と実際の結果、該当ログや画面、関連コード |
| 作業を再開する | 引き継ぎ記録、現在の仕様とコードの変更、実行場所、最後の確認結果 |

例えば、[締切管理の参考例](../examples/deadline.md)で「期限順に並ばない」不具合を直すなら、期限順のDoDと対象タスク、一覧画面と並び替えに関係するコード・テスト、実際に登録した期限と表示順を使います。Copilotへ「10月22日、20日、21日の順で登録したが、そのままの順で表示された。期待は20日、21日、22日の順」と伝えると、何を再現して直すかが分かります。これは説明用の例なので、自分たちの実際の結果を渡してください。

新しい仕様と古い画面が矛盾していたら、その差を明らかにしてチームが決め、正本と画面・テストをそろえます。未入力欄や参考例、仮説を決定済みの事実として扱いません。

仕様や関連コードを変えたら、以前の成功結果が今も有効かを見直します。例えば保存方法を変えた場合、保存・再読み込みなど影響するDoDを再確認します。変更前の結果は日時・対象とともに記録として残し、現在の達成判断には再確認した証拠を使います。[検証記録](../verification.md)にもこの区別を残します。

再開時には、これらの文書と現在のコードから「最後に確かめたこと、未完了、次にすること」を説明してもらいます。過去の会話を全部貼り直す代わりに、決定と証拠が保存されているかを確認します。PCとCodespacesを切り替えるときも、この文書をコードと一緒にGitで渡します。

この教材では、**必要な情報を選ぶ → 実装・確認する → 決定と結果を更新する → 次へ引き継ぐ**という循環で実践します。文書の更新案はCopilotに作ってもらい、学生はチームの決定と実際の結果に合っているかを確認します。

根拠：[AnthropicのContext engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)では、限られた文脈に十分な情報を選び、必要時に取得し、記録を使って継続する考え方を扱っています。[VS Codeのガイド](https://code.visualstudio.com/docs/agents/guides/context-engineering-guide)も、短い共通指示から必要な文書を参照する構成を説明しています。

## 3. 動かす・結果を見る・直す、を繰り返せるようにする

[![ハーネスエンジニアリングの図解：実装・起動・観察・完成条件との照合・修正を繰り返す。mainはアプリ固有の起動・テスト・CIを最初に作り、初心者向けスターターは準備済みの仕組みを使う。](../images/harness-engineering.png)](../images/harness-engineering.png)

mainでは、すべてのアプリに共通する教材と開発環境を残し、**アプリ固有の実行・検証の仕組みは最初のタスクで作ります。** ブランチをコピーした時点でテストやCIが動いているわけではありません。

図で「動かす・結果を見る・直す」の循環を確認したら、最初の実装（[Codespacesの手順5](../codespaces.md#implementation)・[Copilot appの手順5](../copilot-app.md#implementation)）へ戻ります。アプリが動いている場合は、[共通ループの手順3](build-loop.md#3-実装検証修正を続ける)から続きを進めます。 **発表中の振り返りで開いた場合は、[発表ガイドの振り返り](presentation.md#3-copilotとの開発を振り返る)へ戻ります。**

| 仕組み | いつ用意し、どう役立てるか |
| --- | --- |
| [Dev Container](../../.devcontainer/devcontainer.json) | Node 24と任意のコンテナ確認用Dockerを準備。別の言語・実行環境を選んだら必要な設定を追加する |
| [development.md](../development.md) | 構成決定・生成後に、実際に使う依存導入・起動・確認コマンドとポートを記録する |
| 起動・テスト・CI | 最初のタスクで選んだ技術に合わせて生成。起動と最初の操作を確認し、機能追加に合わせDoDのテストを育てる |
| AppのRun設定 | Appで動かす場合、生成したアプリのコマンドを登録。設定がない段階ではRunだけで起動しない |
| 本番コンテナと公開時の確認 | 公開すると決めたときに追加。起動・主要なDoDを確認した同じイメージを配置する |
| [失敗時の記録](verification.md#自動テストが失敗したら) | 必要なログ・画像・操作記録を残す設定を作り、保存先と取得方法も記録する |
| [別の学生による操作確認](verification.md) | テストの期待値自体の間違いや、使いにくさを見つける |

技術を自由に選ぶことと、確認方法を省くことは別です。初回生成の完了は「ファイルができた」ではなく「合意した最小構成が起動し、確認方法を実行できた」とします。React・TypeScript・Vite・Nodeの準備済み環境を選ぶチームには[初心者向けコース](../choose-start.md)があります。

完成条件 → 実装 → 実行・観察 → 条件との照合 → 未達の修正、を繰り返します。結果は文書へ保存し、次の作業・セッションへつなげます。失敗したテストの期待値を都合よく変えず、コードの修正か、チームが合意する仕様変更かを区別します。

### 結果から次の行動を決める

普段の実装・確認で次の行動に迷ったときに、この表を使います。

| 確認できたこと・今の状況 | 次の行動 |
| --- | --- |
| 合意した範囲の不具合が見つかった | 入力・期待結果・実際の結果を基に修正し、同じ条件で再確認する |
| 学生がCodespacesなどで確認中 | AIは確認方法を示し、結果が返るまで次の修正を待つ。結果待ちは「未確認」として扱う |
| 権限・外部サービスの準備・仕様判断が必要、または同じ修正で進展がない | 試したことと必要な操作・判断を伝え、該当作業を止めて相談する |
| 必須DoDの達成と、別の学生による操作確認がそろった | 証拠を記録し、チームが完成を判断する。テストの成功だけでは完成としない |

例えば実際に「期限順に並ばない」不具合が出たら、登録した期限と表示順を確認し、合意したDoDを表すテストで再現します。**修正前の失敗 → 実装修正 → 同じテストの成功 → 学生の操作確認 → 検証記録**の順で、直ったことを確かめます。これは普段の不具合修正で使う例です。手順の詳細は[確認の進め方](verification.md)を使ってください。

生成するCIでは確認の失敗を実行結果へ反映し、公開の仕組みを追加する場合は失敗時に公開へ進まない依存関係を設定します。これは実際のワークフローを作って確かめる制御です。配布時点のmainには、そのCIや公開の制御はまだありません。「結果を待つ」「進展がなければ相談する」といったSkillや依頼文の指示は、AIの報告と人の確認で運用します。**PRのマージを必須チェックで制限する設定は、GitHub側で別途行うもの**です。教材をコピーしただけでマージ制限や課金上限が設定されるわけではありません。Skillや依頼文も、セッション終了後の自動再開を保証する機能ではありません。

根拠：[OpenAIのbest practices](https://learn.chatgpt.com/guides/best-practices)は、適切な文脈・簡潔な共通指示・検証・繰り返す失敗の改善を組み合わせています。[Anthropicの長時間エージェントの設計](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)は、実行環境、進捗の引き継ぎ、実動作の確認を扱っています。各製品固有の自動化機能や記事と同じ性能を、Copilotで再現したという意味ではありません。

## 同じ失敗を繰り返したら、何を直すか

失敗の証拠を見て、原因に合う小さな改善を選びます。毎回すべてのルールやSkillを増やす必要はありません。

| 起きたこと | 改善する場所 | 改善できたかの確かめ方 |
| --- | --- | --- |
| 頼んでいない機能まで作った | 今回の依頼の範囲・対象外 | 同じ依頼を見直し、差分が対象に収まるか確認 |
| 古い仕様や画面で作った | product・画面・参照先 | 次のセッションで現在の仕様を読み取れるか確認 |
| 動いた機能が後の修正で壊れた | 不具合を再現するテスト | 修正前に失敗し、修正後に期待結果で成功するか確認 |
| PCでは動くがCIで動かない | 依存・環境変数・起動設定 | 失敗した環境で同じ確認を再実行 |
| AIの完了報告と実際の動作が違った | DoDと照合するテスト・操作・証拠 | 別の学生も同じ入力と期待結果で確認 |

直したことと確認結果は既存の[検証記録](../verification.md)に、残る作業は[tasks.md](../tasks.md)に残します。再発する共通の問題だけ、短い共通指示や再利用する手順に反映します。不要になったルールは整理します。

テストの成功は、テストで表した条件を満たした証拠です。初回生成のテストや初心者向けスターターのテストだけで、チームの企画が完成したとは判断しません。自分たちのDoDのテストと人の確認を追加し、利用者の困りごとが解決するかも確かめます。
