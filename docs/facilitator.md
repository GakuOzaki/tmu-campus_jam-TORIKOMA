# 運営・メンター向け確認

この教材では、企画と完成条件をチームが決め、Copilotが実装・検証を進め、最後に人が利用者の操作で確かめます。[共通の実装ループ](common/build-loop.md)と[確認方法](common/verification.md)を、どちらの開発環境でも使います。

参加者への案内は[READMEの全体の流れ](../README.md#企画から発表まで)から始め、開発中は選んだ環境ガイドを本線にします。図解は資料準備・Plan・実装の各段階で参照し、公式資料やこの運営ガイドを参加者全員の通読課題にはしません。教材自体の確認範囲と未確認項目は[スターターの検証記録](template-validation.md)を参照します。

## 開催前に確認すること

配布元のGitHubリポジトリは **Settings → General → Template repository** を有効にします。学生が **Use this template** から新しいリポジトリを作れることを、配布前に確認してください。

配布する変更は、それぞれの配布用ブランチへ反映します。`main`は自分たちで構成を決めるコース、`codex/beginner-starter`は初心者向けコースです。[コース選択とコピーの手順](choose-start.md)を、どちらも新しいチーム用リポジトリで確認してください。初心者向けは全ブランチをコピーし、チーム側のデフォルトブランチを`codex/beginner-starter`へ変更します。コース間をマージする手順にはしません。作業用ブランチ上の変更は、選択した配布用ブランチへ反映されるまで教材に含まれません。教材内のPRやCIのリンクは配布元の記録なので、学生チーム自身の成功記録とは区別します。

| 確認対象 | 確認内容 |
| --- | --- |
| 学生アカウント | GitHub Educationの認証だけでなく、Copilot Studentが有効でChatが使えること |
| モデル | 実際の学生アカウントでAutoを選んで応答できること。特定モデル名を操作手順へ追加しない |
| 残量 | CopilotとCodespacesの現在の残量・制限を各自のアカウント画面で確認する |
| チームのリポジトリ | 選んだコースのファイルをコピーでき、デフォルトブランチの設定が一致し、必要なメンバーがアクセスできること。Azure公開を行う場合は[初期設定](common/azure-setup.md)で所有者・公開範囲とEnvironmentの利用条件も確認する |
| Codespaces | 新規作成からブラウザ接続、Terminal・Copilot、Node 24、npm ci、画面とAPIの4280のプレビューまで通ること。開発開始前に環境準備の時間を確保する |
| Copilot app | Git・Appの準備とcloneが通ること。PCで実行する場合はNode 24・設定受け入れ・Setup・Run、Codespacesで実行する場合はPCのSetup・Runを使わずGUIで変更を渡して起動・確認できること |
| 資料の引き継ぎ | 企画メモと画面PNGから、product・tasksの整理ができること |
| 検証 | checkとPlaywright ChromiumのE2E、CIで本番用コンテナのE2Eを実行できること。人のブラウザ確認も行うこと |
| 公開 | PC・Codespacesで確認・発表できること。Azure公開を行う場合は新しいチームリポジトリのOIDC情報で初回設定し、PR→CI→マージ→Container Apps公開→公開URL確認まで通ること |

利用枠の数値はアカウントや提供条件で変わるため、過去の配布資料の数字だけで参加可否を判断しません。[Copilot設定](https://github.com/settings/copilot)、GitHubの **Settings → Billing and licensing**、[Codespaces一覧](https://github.com/codespaces)と[公式プラン説明](https://docs.github.com/en/copilot/get-started/plans)を確認します。

`npm run dev`によるローカル確認にAzureクレジットやDockerは不要です。Azure公開や外部API・共有DBを使うチームは、必要性、利用条件、費用、秘密情報の扱いを確認します。クレジットの有無から、特定のAPIやモデルが必ず使えるとは判断しません。

## 両経路で行うリハーサル

運営の普段のアカウントや既存環境だけで済ませず、可能なら学生相当の権利と新しい作業環境で試します。

1. 初心者向けのコピーとデフォルトブランチ変更を済ませ、[締切管理の例](examples/deadline.md)を使い、[Codespaces](codespaces.md)と[Copilot app](copilot-app.md)をそれぞれ最初からたどります。
2. Planで企画と完成条件を確認し、Agent／Interactiveで一つの操作を実装します。
3. 完成条件に対応する機能テストを確認します。並び替えなど期待値が明確な処理では、未実装時の失敗と実装後の成功も確かめます。
4. `npm run check`、`npm run test:e2e`、人の操作確認を実施します。
5. 仕様を一つ変更し、product、tasks、テスト、実装、verificationが一致するところまで戻します。
6. sessionを終了して再開し、保存されたファイルから作業を継続できるか確認します。
7. Copilot appのGUIでcommit・pushし、初回はその作業ブランチからCodespaceを作成、再利用時はGUIのPullで取り込んで4280から確認する経路も通します。
8. 選んだコースから作った作業ブランチのPRが、チームのデフォルトブランチへ向いていることと、CIで本番用コンテナのテストを確認します。[Codespacesでの手動コンテナ確認](common/local-development.md#コンテナで確認する任意)も運営で通します。Azure公開を行う場合はContainer Appsの公開URLを別のブラウザで開き直し、APIや実際の認証も確かめます。

9. マージ後は最新のチームのデフォルトブランチから新しい作業ブランチを作り、発表後の記録も次のPRで共有できることを[再開手順](common/build-loop.md#after-merge)で確認します。保存・PR・CIの後に[発表・振り返り・終了](common/presentation.md)へ到達し、Azureを使わなくてもプレビューでデモできることを確認します。資料・図解・参考例を開いた後、対応する環境手順へ戻れることも確かめます。

確認の記録には、日付、OS、VS Code／Appのバージョン、アカウントのプラン、実行経路、成功した項目、失敗・未確認項目を残します。アクセストークン、個人のメールアドレス、私的な会話の原文は記録しません。

**このチェックリストを掲載しただけではリハーサル完了ではありません。** リポジトリ内でのbuild・テスト成功と、コンテナの起動・テスト、学生アカウントでのCopilot操作、Codespaces、App、Azure Container Apps公開の成功は別々に記録します。未実施の項目は「未確認」のまま扱います。

## 当日の支援

困っているチームには、まず「期待した操作」「実際に起きたこと」「エラー表示」「最後に動いた状態」を聞きます。漠然と再生成する前に、確認できる小さな問題へ分けます。

| 状況 | 支援の方針 |
| --- | --- |
| 企画が広すぎる | 最初に通す利用者の操作を一つ決め、残りは今回の対象外へ移す |
| AIが完成と報告する | productの完成条件とverificationの証拠を照合し、未確認を探す |
| テストは通るが画面が動かない | 実際の操作手順を再現し、ブラウザの結果とログを渡す |
| テストが形だけになっている | 要求を満たさない実装でも成功しないか確認し、期待結果を見直す |
| AIによるブラウザ操作が使えない | 人がブラウザで操作し、結果や画像をCopilotへ渡す |
| MCPやFigma接続で止まる | 画面PNG＋操作・遷移メモで実装を続ける |
| 会話が長くなった | product・tasks・verificationを更新して、次のsessionへ引き継ぐ |
| 未達なのに同じ修正を繰り返す | 一度止め、失敗の証拠と前提をメンターと確認する |

判断が変わった場合は、完成条件を黙って削るのではなく、チームが変更理由を決めてproductとtasksへ反映します。テストを通すために要件を弱めることと、利用者に必要な範囲を選び直すことを区別します。

## 完成を判定する材料

- **仕様**：誰のどの場面で役立つか、最初の操作、完成条件が説明できる。
- **機械の確認**：checkと必要な機能テストが成功し、何を確認したかが残っている。
- **人の確認**：実装した人とは別の学生が、必須DoDに対応する主要な操作経路と、その機能に関係する空の状態・入力ミス・スマートフォン幅を確かめ、結果を記録している。
- **未確認**：制限・未実装・外部サービスの未接続を隠さず説明できる。
- **発表**：公開URLまたは動作するプレビューと、企画から変更した点を示せる。

チェックの成功だけで利用者の課題が解決したとは決めません。短い利用者テストから気づいたことを、改善や発表へつなげます。

## 開発の工夫を振り返る

参加者の[発表・振り返り](common/presentation.md)と同じ3つの観点を使います。資料準備でコンテキスト、Plan直前にプロンプト、実装直前にハーネスの図解を見たうえで、実際に役立ったことを短く話してもらいます。

開発中に次の行動に迷ったら、[結果から次の行動を決める表](common/ai-development-tips.md#結果から次の行動を決める)を使います。短い開発時間でも、普段の実装・確認の中でハーネスの考え方を学べます。追加の演習は設けず、時間に余裕があれば、一つの機能を作り終えたところで[3つの工夫](common/ai-development-tips.md)を見ながら短く振り返ります。

1. **依頼**：何を頼み、どの入力・期待結果で具体化したか。
2. **情報**：判断に使った資料は何か。新しいセッションでも現在の決定を読めるか。
3. **仕組み**：実行して得た証拠は何か。失敗や見落としを次に見つける方法があるか。

実際に繰り返した失敗があれば、依頼・資料・テスト・環境のうち改善する場所を選び、変更後も同じ条件で確かめます。既存のverification・tasksへ結果を残し、追加した指示の長さやSkillの数で良し悪しを判断しません。

## 終了時

[参加者の終了手順](common/presentation.md)に沿って、発表でプレビューを使い終えた後に保存・pushを確認し、Codespacesを停止します。Copilot appのRunで起動したサーバーは **Stop Run**、Terminalで起動したサーバーやコンテナはそのTerminalで終了します。Browserの画面が残っているかどうかだけで稼働・停止を判断しません。Azure公開を行ったチームは、継続利用するか、公開手順に沿って不要なリソースを削除するかも決めます。継続開発するチームは、残りのタスクと次に確認することをファイルへ残します。
