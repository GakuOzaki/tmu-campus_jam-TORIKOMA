# 運営・メンター向け確認

この教材では、企画と完成条件をチームが決め、Copilotが実装・検証を進め、最後に人が利用者の操作で確かめます。[共通の実装ループ](common/build-loop.md)と[確認方法](common/verification.md)を、どちらの開発環境でも使います。

開催前は[設計の根拠](references.md)と[教材の検証記録](template-validation.md)で前提・未確認を読み、下のリハーサルへ進みます。当日の参加者には[READMEの全体の流れ](../README.md#企画から発表まで)を入口として案内し、開発中は選んだ環境ガイド、最後は[発表と終了](common/presentation.md)へつなぎます。運営資料の通読を学生の必須手順にはしません。

## 開催前に確認すること

参加者は、リポジトリを作る前に[開始コースの選び方](choose-start.md)で次のどちらかを決めます。開発環境のCodespaces／Copilot appとは別の選択です。

- **main：企画から構成を選ぶ。** アプリの雛形なし。Dev Container、Copilotへの共通指示・Skills、企画・開発・検証の文書を使い、最初のタスクでアプリ・必要なテスト・CIを生成します。
- **codex/beginner-starter：準備済みの構成を使う。** React・TypeScript・Vite・Node、起動・テスト・コンテナ・CIの基盤を使い、機能開発に集中します。

配布元の **Settings → General → Template repository** を有効にし、学生が **Use this template** から作成できることを確認します。mainだけをコピーする操作と、**Include all branches**を選んで初心者向けブランチもコピーする操作は異なります。初心者向けでは、作成先の既定ブランチを含めて[選択手順](choose-start.md)どおり設定し、そのブランチのREADMEから進めます。ブランチを表示してからコピーしただけで、その内容だけが自動的に選ばれるとは考えません。

配布前に両コースの更新をそれぞれの配布ブランチへ反映します。未マージのPRの内容が自動的にmainへ入ることはありません。教材内のPRやCIのリンクは配布元・過去の検証用リポジトリの記録で、学生チーム自身の成功記録とは区別します。

| 確認対象 | 確認内容 |
| --- | --- |
| 学生アカウント | GitHub Educationの認証だけでなく、Copilot Studentが有効でChatが使えること |
| モデル | 実際の学生アカウントでAutoを選んで応答できること。特定モデル名を操作手順へ追加しない |
| 残量 | CopilotとCodespacesの現在の残量・制限を各自のアカウント画面で確認する |
| チームのリポジトリ | 選択したコースの内容で作成でき、既定ブランチと必要なメンバーのアクセスを確認する。公開する場合は所有者・イメージの公開範囲・Azure権限も確認する |
| Codespaces | 新規作成、Terminal・Copilot、必要な実行環境が使えること。mainでは生成前にアプリ起動を求めず、生成後にdevelopment.mdのコマンド・ポートで確認する。準備時間も確保する |
| Copilot app | Git・Appを準備する。PCで実行する場合は採用技術の実行環境と生成後のSetup・Runを確認する。Codespacesで実行する経路では、PC用の実行環境・Setup・Runを必須にしない |
| 資料の引き継ぎ | 企画メモと画面PNGからproduct・tasksを整理し、mainでは構成を合意してdevelopment.mdを更新できること |
| 検証 | 構成に合うテスト・CIが実行され、人のブラウザ確認とともに記録されること。mainでの未生成・未実行のCIは未確認。公開する場合はコンテナの確認も通す |
| 公開 | PC・Codespacesで確認・発表できること。公開を選ぶ場合はコースの手順でPR・CI・確認済みイメージの公開・Container Apps配置・公開URL確認まで通ること |

利用枠の数値はアカウントや提供条件で変わるため、過去の配布資料の数字だけで参加可否を判断しません。[Copilot設定](https://github.com/settings/copilot)、GitHubの **Settings → Billing and licensing**、[Codespaces一覧](https://github.com/codespaces)と[公式プラン説明](https://docs.github.com/en/copilot/get-started/plans)を確認します。

通常の開発サーバーで確認する場合、AzureクレジットやDockerは不要です。Azure公開や外部API・共有DBを使うチームは、必要性、利用条件、費用、秘密情報の扱いを確認します。クレジットの有無から、特定のAPIやモデルが必ず使えるとは判断しません。

## 両コース・両経路で行うリハーサル

運営の普段のアカウントや既存環境だけで済ませず、可能なら学生相当の権利と新しい作業環境で試します。

1. [選択手順](choose-start.md)から新しいチームリポジトリを作り、mainと初心者向けの両コースで、選んだ内容・既定ブランチになっていることを確認します。
2. [締切管理の例](examples/deadline.md)を使い、[Codespaces](codespaces.md)と[Copilot app](copilot-app.md)をそれぞれ最初からたどります。初心者向けコースは、そのブランチ内のガイドを使います。
3. mainではPlanで最小構成を合意し、Agent／Interactiveでアプリ・テスト・CIを生成し、起動・確認方法をdevelopment.mdへ記録します。初心者向けでは準備済みの起動を確認します。
4. 一つの利用シナリオを実装し、DoDのテストと別の人の操作確認を行います。期待値が明確な処理では、修正前の失敗と修正後の成功も確かめます。
5. 仕様を一つ変更し、product・tasks・テスト・実装・verificationをそろえます。mainではdevelopment.md、初心者向けではそのコースの開発手順と実際の設定も合わせます。
6. sessionを終了して再開し、保存された文書から現在の構成・決定・未完了を読み、続きを進められることを確認します。
7. Copilot appのGUIでcommit・pushし、初回はその作業ブランチからCodespaceを作成、再利用時はGUIのPullで取り込みます。記録された準備・起動方法で確認して結果をAppへ返す経路も通します。
8. PRのCIが実際に動き、結果と実行URLを記録できることを確認します。公開するチーム向けには、Dockerfile・コンテナテスト・レジストリへの保存・同じdigestの配置・公開URLの操作まで別に通します。

確認の記録には、日付、OS、VS Code／Appのバージョン、アカウントのプラン、実行経路、成功した項目、失敗・未確認項目を残します。アクセストークン、個人のメールアドレス、私的な会話の原文は記録しません。

**このチェックリストを掲載しただけではリハーサル完了ではありません。** 文書・設定の検査、生成したアプリのbuild・テスト、コンテナの確認、学生アカウントでのCopilot操作、Codespaces、App、Azure公開の成功は別々に記録します。過去の初心者向け構成のCI成功をmainの生成経路の成功として転用しません。未実施の項目は「未確認」のまま扱います。

## 当日の支援

困っているチームには、まず「期待した操作」「実際に起きたこと」「エラー表示」「最後に動いた状態」を聞きます。漠然と再生成する前に、確認できる小さな問題へ分けます。

| 状況 | 支援の方針 |
| --- | --- |
| 企画が広すぎる | 最初に通す利用者の操作を一つ決め、残りは今回の対象外へ移す |
| AIが完成と報告する | productの完成条件とverificationの証拠を照合し、未確認を探す |
| テストは通るが画面が動かない | 実際の操作手順を再現し、ブラウザの結果とログを渡す |
| テストが形だけになっている | 要求を満たさない実装でも成功しないか確認し、期待結果を見直す |
| AIによるブラウザ操作が使えない | 人がブラウザで操作し、結果や画像をCopilotへ渡す |
| MCPやFigma接続で止まる | 画面PNG＋操作・遷移メモで実装を続ける |
| 会話が長くなった | product・tasks・verificationを更新して次のsessionへ引き継ぐ。mainではdevelopment.md、初心者向けでは開発手順と設定も確認する |
| 未達なのに同じ修正を繰り返す | 一度止め、失敗の証拠と前提をメンターと確認する |

判断が変わった場合は、完成条件を黙って削るのではなく、チームが変更理由を決めてproductとtasksへ反映します。テストを通すために要件を弱めることと、利用者に必要な範囲を選び直すことを区別します。

## 完成を判定する材料

- **仕様**：誰のどの場面で役立つか、最初の操作、完成条件が説明できる。
- **機械の確認**：mainではdevelopment.md、初心者向けではそのコースの開発手順に記載した確認と、必要な機能テスト・CIが成功し、対象の変更と確認内容が残っている。
- **人の確認**：実装した人とは別の学生が、必須DoDに対応する主要な操作経路と、その機能に関係する空の状態・入力ミス・スマートフォン幅を確かめ、結果を記録している。
- **未確認**：制限・未実装・外部サービスの未接続を隠さず説明できる。
- **発表**：公開URLまたは動作するプレビューと、企画から変更した点を示せる。

チェックの成功だけで利用者の課題が解決したとは決めません。短い利用者テストから気づいたことを、改善や発表へつなげます。

## 開発の工夫を振り返る

参加者自身の振り返りは、[発表ガイドの3つの問い](common/presentation.md#3-copilotとの開発を振り返る)にまとめています。下の観点は、メンターが途中で支援するときにも使えます。

開発中に次の行動に迷ったら、[結果から次の行動を決める表](common/ai-development-tips.md#結果から次の行動を決める)を使います。短い開発時間でも、普段の実装・確認の中でハーネスの考え方を学べます。追加の演習は設けず、時間に余裕があれば、一つの機能を作り終えたところで[3つの工夫](common/ai-development-tips.md)を見ながら短く振り返ります。

1. **依頼**：何を頼み、どの入力・期待結果で具体化したか。
2. **情報**：判断に使った資料は何か。新しいセッションでも現在の決定を読めるか。
3. **仕組み**：実行して得た証拠は何か。失敗や見落としを次に見つける方法があるか。

実際に繰り返した失敗があれば、依頼・資料・テスト・環境のうち改善する場所を選び、変更後も同じ条件で確かめます。既存のverification・tasksへ結果を残し、追加した指示の長さやSkillの数で良し悪しを判断しません。

## 終了時

[発表ガイドの終了手順](common/presentation.md#4-発表後に保存して終了する)に沿い、デモが終わってから停止するよう案内します。

保存・pushを確認し、Codespacesを停止します。Copilot appの開発サーバーと、手動起動したコンテナはTerminalで終了します。Azure公開を行ったチームは、継続利用するか、公開手順に沿って不要なリソースを削除するかも決めます。継続開発するチームは、残りのタスクと次に確認することをファイルへ残します。
